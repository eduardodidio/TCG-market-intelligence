# F94-T03: CLI Manual Backup/Restore to R2

**Status:** planned
**Wave:** 1
**Depends on:** T01, T02

## User Story

As an operator, I want CLI commands to manually trigger a backup to R2 or
restore from R2, so I can recover from disasters or migrate between
environments without relying solely on Litestream's automatic replication.

## Dev Notes

### Changes

1. **src/database/backup.py** — Add two functions:
   - `backup_to_r2(db_path, bucket, endpoint, key_id, secret_key)`:
     Uses `litestream snapshots` or direct S3 upload via `boto3`/`httpx`
     to push a consistent SQLite snapshot to R2.
     Simpler approach: just call `litestream replicate` once in snapshot
     mode, or use the existing `backup_database()` to create a local copy
     then upload via presigned PUT.
   - `restore_from_r2(db_path, bucket, endpoint, key_id, secret_key)`:
     Calls `litestream restore` subprocess, or downloads the latest
     snapshot via S3 GET and replaces the local file.

2. **src/cli/main.py** — Add commands:
   ```
   tcg db-backup-r2   # push current DB to R2
   tcg db-restore-r2  # pull latest DB from R2
   ```
   Both read R2 credentials from env vars (same as Litestream config).

3. **Alternative (simpler)**: Instead of boto3, just shell out to
   `litestream restore` / `litestream replicate` subprocess. This avoids
   a new dependency and reuses the same config file.

### Key decisions

- Prefer subprocess calls to `litestream` binary over adding boto3 dep
- These commands are for emergency use — normal flow is automatic via
  Litestream sidecar
- Restore command warns and requires `--confirm` flag (destructive:
  overwrites local DB)

## Testing

- [ ] `db-backup-r2` succeeds when Litestream is installed and configured
- [ ] `db-backup-r2` fails gracefully when Litestream is not installed
- [ ] `db-restore-r2 --confirm` restores a previously backed up DB
- [ ] `db-restore-r2` without `--confirm` prints warning and exits
- [ ] Unit tests mock subprocess calls
