## Findings

### IMPORTANT — `daily_snapshot_backfill` priority doesn't match the ADR

`src/collection/price_history_keys.py::SOURCE_PRIORITY` lists `manual: 0,
liga: 1, jsonld_snapshot: 2, myp: 3, daily_snapshot: 9` but has **no entry
for `daily_snapshot_backfill`**. `source_priority()` falls back to
`UNKNOWN_SOURCE_PRIORITY = 5` for it. ADR 0017 explicitly says (Decision
§4, "Backfill marker"): *"The resolver and merge treat it exactly like
`daily_snapshot`: the same keys per variant, **priority 9**, and it does
not count as a 'real' point."* The keys part is implemented correctly
(`_with_backfill_keys` in `collection_price_history.py`); the **priority**
part is not — backfill sits at priority 5, i.e. above (wins over) `myp`'s
priority-3 tier is impossible since 5 > 3, but it wins over `jsonld_snapshot`
is also impossible (2 < 5), the one case that inverts intent is
`daily_snapshot_backfill` (5) beating a real `daily_snapshot` (9) whenever
both exist for the *same day* under *different keys* of the same variant
(e.g. a `liga_{id}_foil` real snapshot and a `manual_{id}` backfill row
landing on the same date). Both count as "snapshot, not real" in `meta`
either way, so `real_points`/`snapshot_points` aren't affected, but which
row's *price* gets displayed for that day is nondeterministic relative to
the documented contract.

This was flagged as an open gap in the Wave 2 summary ("follow-up needed")
and repeated in the Wave 3 summary ("not addressed... still a latent gap"),
and never fixed by Wave 4. There is also no test exercising a same-day tie
between `daily_snapshot` and `daily_snapshot_backfill` in either
`tests/collection/test_price_history_keys.py` or
`tests/services/test_collection_price_history.py` — the existing service
test (`test_only_snapshots_have_no_first_real_observation`) places them on
different days, so it doesn't catch this.

**Fix:** add `"daily_snapshot_backfill": 9,` next to `SNAPSHOT_SOURCE: 9`
in `SOURCE_PRIORITY`, plus a regression test for the same-day tie (both
sources present on one day, assert the merge doesn't panic and picks a
deterministic winner). Small, safe, no schema/contract change — should
land before this batch promotes to `main`.

**APPROVED_WITH_FOLLOWUP**

All 12 tasks are implemented, tested, and match ADR 0017 / the brief. The
architecture is clean (one pure resolver, one service, three thin callers),
off-limits files were correctly left untouched, diagrams and README were

batch, since it's a one-line dict entry plus a test) before promoting to
`main`. Promotion itself remains blocked on the pending-user AC15/Neon
validation regardless of this review's verdict.
