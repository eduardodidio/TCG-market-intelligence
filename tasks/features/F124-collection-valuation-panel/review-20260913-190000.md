## T06 — Record fetched Liga URL in all Liga price writers

1. All 5 writers (`liga_sweep.py`, `scan.py`, `collection.py` refresh-liga,
   `cards.py` refresh, `cli/main.py` push-prices) call
   `record_liga_url`/`upsert_liga_card_url` right after a successful price
   observation, via the shared `src/collectors/liga_url_recorder.py` helper,
   which never raises (catches `Exception`, logs, returns `False`).
2. **BLOCKING** — `tests/collectors/test_liga_sweep.py::test_fetch_liga_price_prefers_low_over_mid`
   fails against the current code. `src/collectors/liga_sweep.py:63` does
   `price = normal.get("mid") or normal.get("low") or normal.get("high")`
   (mid-first, correct per the CLAUDE.md guardrail "Liga sweep usa preco `mid`,
   NAO `low`"), but the test (pre-existing since the F82 "lowest price strategy"
   commit, confirmed via `git show HEAD:...` — the assertion predates F124)
   still asserts `low` (1.00) wins over `mid` (2.00). Verified by running it
   directly: `AssertionError: assert Decimal('2.00') == Decimal('1.00')`. T06
   touched this exact test file (added `page_url` tuple-unpacking to every
   assertion in it, including this one's) but did not notice the mismatch while
   doing so. This is a pre-existing staleness, not an F124 regression in
   behavior — but F124 touched the file and the fix is a one-line assertion
   correction (`Decimal("1.00")` → `Decimal("2.00")`, and rename the test to
   reflect mid-first, since "prefers_low_over_mid" is now a misleading name).
   **Required before merge** — it's mechanical, low-risk, and directly
   contradicts a documented guardrail while sitting inside a file this feature
   modified.
3. **IMPORTANT** — `src/cli/main.py:1520-1547` (`_push_prices_async`,
   `push-prices` command): `record_liga_url` (line 1542, new in this diff) writes
   to the **local** repo's `liga_card_urls` table, but the price observation
   itself is only queued and pushed to a **remote** server over HTTP later
   (lines 1580-1594), and only when `dry_run=False`. Two consequences: (a) in
   `dry_run=True` mode the local `liga_card_urls` table is still permanently
   mutated even though no price is stored anywhere — confirmed intentional by
   `tests/cli/test_push_prices.py::test_push_prices_records_liga_url`, which runs
   with `dry_run=True` and still asserts the upsert happened; (b) even in a real
   run, the URL lands in the local DB while the matching price lands in the
   remote DB, so the two never coexist in the same database — `get_liga_card_url`
   on either side can return a URL with no corresponding price row, which breaks
   the "link always matches the price shown" guarantee this feature is built
   around, specifically for this one writer. `push-prices` is already flagged in
   CLAUDE.md as largely superseded by the direct-to-Neon `liga-sweep` workflow,
   which lowers the real-world blast radius — but the code as written is
   internally inconsistent. **Recommend as a follow-up**: either skip URL
   recording in this command entirely (since it doesn't own the local price row),
   or gate it on `not dry_run` for consistency with the price push. Ask the user
   which they'd prefer before changing it, since it touches the (deprecated but
   still present) push-prices flow.
4. Verdict: **approve pending the one BLOCKING fix**.

## Retrospective Seeds

- **Pattern:** When a task touches a test file only to update an unrelated
  mechanical detail (here: unpacking a new tuple return value into every
  assertion in the file), the developer re-typed/adjusted every assertion
  without re-validating that each one still describes real behavior. A stale,
  already-wrong assertion silently rode along.
  **Role(s) affected:** developer, techlead.
  **Lesson:** When a task requires touching every test in a file for a
  mechanical reason (return-type change, signature change), run the full file
  once before and after the mechanical edit and diff the pass/fail set — don't
  assume "I only changed unpacking syntax" means no behavioral assertions could
  be affected. TechLead should specifically check, in tasks with this pattern,
  whether every touched assertion is still green, not just whether the touched
  file's syntax is consistent.
- **Pattern:** A "record the fetched URL" writer helper was added uniformly to
  5 call sites including a CLI command whose local DB and remote DB are
  different databases by design. Uniform helper reuse across writers is
  usually good, but one of the 5 call sites had a structurally different
  data-flow (local write + remote push) that the shared helper's assumption
  (URL and price land in the same DB) didn't hold for.
  **Role(s) affected:** architect, developer.
  **Lesson:** When a Wave manifest says "add X to all N writers," explicitly
  check whether all N writers share the same read/write topology (same DB,
  same transaction boundary) before applying a shared helper uniformly — list
  each writer's DB target as a line item in the task spec, not just "all Liga
  price writers."
