## User Story

As a user, I want to see prices on as many cards as possible in market movers
and explore cards pages.

## Dev Notes

### Diagnosis approach

1. Check how many cards have price observations:
   ```sql
   SELECT COUNT(DISTINCT external_id) FROM price_observations;
   SELECT COUNT(*) FROM cards;
   ```
   If ratio is low, most cards simply have no price data collected yet.

2. Check if `get_latest_prices_batch()` query is too restrictive:
   - It joins on `source_cards` — cards without a `source_card` link won't have prices
   - Cards must have been scanned via `snapshot-prices` or `scan` CLI

3. Check `get_movers()` query — requires at least 2 observations (start and end)
   for the period. Cards with only 1 observation won't appear.

### Likely root cause

- Most cards have at most 1 price observation (from a single scan)
- Market movers needs 2+ observations across different dates
- This is a **data coverage issue**, not a bug

### Possible fixes

1. **Lower movers threshold**: if a card has only 1 observation, show it with
   0% change (static) — but this defeats the purpose of "movers"
2. **Show static prices in explore**: cards with 1 observation SHOULD show
   a price in explore cards. If they don't, it's a query bug.
3. **Run more scans**: the real fix is running `scan` periodically to build
   price history

### Action items

3. Document that movers requires 2+ observations (expected behavior)
4. Ensure `start.sh` or cron runs scans regularly

## Diagnostic Results (2026-08-21)

### Data coverage summary

| Metric | Value |
|--------|-------|
| Total cards in DB | 349 |
| Cards with source_card link | 349 (100%) |
| Total price observations | 2,000 |
| Distinct external_ids with observations | 141 (40.4% of cards) |
| Cards returning a non-zero price via `get_latest_prices_batch` | 140 |
| External IDs with 2+ observation dates (eligible for movers) | 30 |
| Observations with NULL or 0 median_price | 12 |
| Observation date range | 2023-08-20 to 2026-08-20 |

### Root cause: data coverage, not a code bug

- **Explore cards**: 209 of 349 cards (59.6%) show no price because they have
  zero price observations. The remaining 140 cards correctly show prices.
  The `get_latest_prices_batch()` query is correct -- it joins `source_cards`
  to `price_observations` via `external_id` and returns the most recent
  observation. No query bug found.

- **Market movers**: only 30 external_ids have observations on 2+ distinct
  dates. This is by design -- movers requires a start and end price to
  compute % change. The `get_movers()` query correctly finds earliest and
  latest observations within the period. With 30 eligible cards, the top-10
  gainers and losers lists are populated (verified: 10 gainers, 10 losers
  for 30d/90d/365d periods).

- **1-card discrepancy** (141 SQL vs 140 repository): one card's latest
  observation has a NULL or zero `median_price`, so it is excluded by the
  `if obs.median_price` check in the API layer. This is correct behavior.

### Resolution

No code changes needed. The fix is operational:

1. Run `python -m src.cli.main scan` periodically to build price coverage
   for more cards.
2. Run scans on multiple dates to enable movers calculations (need 2+
   distinct observation dates per card).
3. The `start.sh` script or a cron job should schedule regular scans.

### Queries verified correct

- `get_latest_prices_batch()` -- correctly joins source_cards + price_observations
- `get_movers()` -- correctly requires earliest + latest observation with non-null prices
- `list_cards` API endpoint -- correctly calls `get_latest_prices_batch` and converts prices
