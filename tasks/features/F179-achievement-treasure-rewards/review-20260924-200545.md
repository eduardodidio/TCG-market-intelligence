## Context

The previous review rejected F179 for a double-credit race in
`credit_reward_in_session`: the ledger existence check ran *before* the
`CreditBalanceRow.with_for_update()` lock was acquired, contradicting
ADR-0020 §2 and allowing two concurrent backfills to both credit the same
`(user_id, achievement_key)` on PostgreSQL (SQLite's single-writer lock
masked it). Commit `9519b44` claims to fix the ordering.

## 1. Fix verification against ADR-0020 §2

Read `src/services/achievement_rewards.py:72-114` (current):

```python
bal = session.execute(
    select(CreditBalanceRow).where(CreditBalanceRow.user_id == user_id).with_for_update()
).scalar_one_or_none()

exists = session.execute(
    select(CreditTransactionRow.id).where(...).limit(1)
).first()
if exists:
    return 0

if bal is None:
    bal = CreditBalanceRow(user_id=user_id, balance=0)
    session.add(bal)
    session.flush()

bal.balance += amount
session.add(CreditTransactionRow(...))
```

This now matches ADR-0020 §2 exactly: the balance row is locked first, and
the ledger existence check is the statement that runs (and is re-evaluated)
under that lock. On PostgreSQL, a second concurrent transaction blocks at
the `with_for_update()` line until the first commits or rolls back; when it
resumes, its `exists` check runs against the post-commit snapshot (new
statement under READ COMMITTED) and correctly sees the first transaction's
`CreditTransactionRow`, returning `0`. The TOCTOU window from the previous
review is closed. **Confirmed fixed.**

The new test `TestCreditLockOrdering.test_balance_row_locked_before_ledger_check`
asserts the statement order directly (balance-table `SELECT ... FOR UPDATE`
executes before the `credit_transactions` `SELECT`), which is an
appropriate way to pin the ordering given SQLite can't reproduce the actual
race — same mitigation the previous review's Retrospective Seeds asked for.

## 2. Residual edge case (not blocking, not part of the rejection)

When `bal is None` (a user with no `CreditBalanceRow` at all yet — e.g.
first-ever credit for a brand-new account), `with_for_update()` on a query
that matches zero rows takes no lock, since there is no row to lock. Two
concurrent transactions crediting that same never-before-credited user
could then both observe `bal is None` and both `INSERT` a
`CreditBalanceRow`; the `unique=True` constraint on `credit_balances.user_id`
(`src/database/models.py:319`) means the second insert raises
`IntegrityError` rather than double-crediting — a crash, not silent
duplication, and `backfill_all_rewards` already wraps each user in a
`try/except Exception` (`achievement_rewards.py:175-177`), so this fails
safe (counted as `errors += 1`, logged, retryable) rather than corrupting
the ledger.

This is not a regression introduced by `9519b44` (the get-or-create-without-
lock shape predates the fix and mirrors the exact same pattern already in
production in `repository.py:3692-3699` (`update_credit_balance`), which
this feature reuses rather than duplicates), it does not double-credit, and
it is not the race AC3/ADR-0020 §2 were written to close. Not blocking this
re-review. Worth a follow-up ADR note if the team wants a DB-level guarantee
(ADR-0020's own "Future improvement" section already anticipates a partial
unique index on `credit_transactions` for defense-in-depth — that same
index would also close this narrower gap).

## Verdict

**APPROVED**

The double-credit race identified in the previous review is closed: the
implementation now locks the balance row before the ledger check, matching
ADR-0020 §2 verbatim, and a targeted test pins the statement ordering so a
regression back to check-then-lock would be caught even on SQLite. AC3 is
satisfied. All previously-approved areas (architecture, test coverage,
diagrams, cross-task consistency) stand unchanged from the prior review.

  named, with no unrelated changes — this made re-review fast and low-risk

  `repository.py:update_credit_balance`), both relying on the
  `credit_balances.user_id` unique constraint plus caller-side exception
  handling to fail safe instead of double-crediting. **Role(s) affected:**
  architect, techlead. **Lesson:** if a future feature adds a fast path
  that writes `credit_transactions`/`credit_balances` without going through
  `update_credit_balance`/`credit_reward_in_session`, verify it has the
  same fail-safe (unique constraint + try/except) rather than assuming
  `with_for_update()` alone makes first-time balance-row creation race-free.
