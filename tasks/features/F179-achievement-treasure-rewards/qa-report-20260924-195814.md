## Blocking defect (confirmed independently)

`src/services/achievement_rewards.py::credit_reward_in_session` (lines
~80–106):

```python
exists = session.execute(select(CreditTransactionRow.id).where(...)).first()   # (1) check
if exists:
    return 0
bal = session.execute(select(CreditBalanceRow)...with_for_update()).scalar_one_or_none()  # (2) lock
...
session.add(CreditTransactionRow(...))                                          # (3) insert, not re-checked under (2)
```

ADR-0020 §2 states the lock must be acquired **before** the existence
check ("locks the user's `CreditBalanceRow` with `.with_for_update()` ...
before checking whether a ledger row ... already exists"). The shipped
code does check-then-lock, not lock-then-check, so two concurrent
sessions on PostgreSQL can both pass step (1), then both proceed through
step (2) (which only serializes the balance mutation, not the existence
re-check), and both insert a `credit_transactions` row for the same
`(user_id, reason, reference_id)` — there is no unique DB constraint to
catch it (confirmed: no such index in `src/database/models.py`, by ADR's
own design). This hits hardest on `backfill_user_rewards_in_session` /
the CLI backfill, which has no `AchievementRow`-unique-insert gate in
front of it the way the primary unlock path does.

SQLite cannot reveal this: its single-writer file lock serializes all
writes regardless of `with_for_update()`, so
`TestConcurrency.test_concurrent_check_calls_credit_exactly_once` in
`tests/integration/test_f179_achievement_rewards.py` passes while only
covering the *new-unlock* case (protected separately by the
`AchievementRow` unique constraint), not the backfill race the ADR was
written to prevent. There is no test that concurrently backfills a
*pre-existing* unlocked-but-uncredited achievement for the same user —
this is the exact gap TechLead flagged, and it remains open.

**Fix required (per TechLead, confirmed correct by QA):** in
`credit_reward_in_session`, acquire the `CreditBalanceRow`
`.with_for_update()` lock first, then re-run the existence check under
that lock, then insert. This is a small, local change with no schema
impact. A companion test is needed that seeds a pre-existing
`AchievementRow` (bypassing the unlock-path gate) and drives two
concurrent `backfill_user_rewards_in_session` calls for the same user —
ideally against Postgres in CI, since SQLite cannot exercise this path.

QA did not apply this fix: it is a concurrency-correctness change to
core crediting logic (money-equivalent, Treasure tokens) and belongs
with the Developer role per the Waves workflow, with TechLead re-review
of the corrected lock ordering. Re-running QA after the fix lands is
recommended rather than QA patching around a rejected implementation.
