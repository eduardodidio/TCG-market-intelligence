## 2. Code quality

- `ACHIEVEMENT_TIERS` maps all 11 achievement keys defined in
  `ACHIEVEMENT_DEFINITIONS` (AC1) — verified by listing both.
- The `treasure_hunter` fix (`reason.in_(("bonus", "bonus_claim"))`) is
  correct: `src/credits/service.py`'s `claim_bonus` writes
  `reason="bonus_claim"`, so the achievement could never fire before.
- **BLOCKING — idempotency race does not match its own ADR.**
  `docs/adr/0020-achievement-reward-ledger-idempotency.md` §2 states the
  backfill path "locks the user's `CreditBalanceRow` with
  `.with_for_update()` ... **before** checking whether a ledger row ...
  already exists." The actual code
  (`src/services/achievement_rewards.py:80-98`,
  `credit_reward_in_session`) does the opposite:
  ```python
  exists = session.execute(select(CreditTransactionRow.id).where(...)).first()  # no lock yet
  if exists:
      return 0
  bal = session.execute(select(CreditBalanceRow)...with_for_update()).scalar_one_or_none()  # lock acquired here
  ...
  session.add(CreditTransactionRow(...))  # insert happens after the check, not re-verified under the lock
  ```
  Because the existence check runs *before* the row lock is taken, two
  concurrent sessions can both see "not yet credited", then serialize only
  on the balance-row lock — and both still credit and insert a ledger row
  for the same `(user_id, reason, reference_id)`, since there is no unique
  constraint on `credit_transactions` to catch the duplicate at the DB
  level (confirmed: no such index in `src/database/models.py`).
  - This specifically affects the **backfill path**
    (`backfill_user_rewards_in_session`, and the CLI's
    `backfill_all_rewards`), which — unlike the unlock path — has no
    `AchievementRow` unique-insert serialization point in front of it.
    Two concurrent `POST /achievements/check` calls for a user with a
    pre-F179 unlocked-but-uncredited achievement can double-credit it on
    Postgres.
  - SQLite masks this: SQLite's single-writer file lock serializes all
    writes regardless of `with_for_update()` (a no-op on that dialect), so
    `TestConcurrency.test_concurrent_check_calls_credit_exactly_once` in
    `tests/integration/test_f179_achievement_rewards.py` passes but only
    exercises the *primary unlock* path (a brand-new `first_card`
    achievement, protected by the `AchievementRow` unique constraint), not
    the backfill race the ADR is actually trying to prevent. There is no
    test that concurrently backfills a *pre-existing* unlocked achievement
    for the same user, which is exactly the scenario the bug hits.
  - **Fix:** move the existence check to after acquiring the balance-row
    lock (re-check under the lock before crediting), matching what the ADR
    already describes. This is a small, local change to
    `credit_reward_in_session` — no schema change required.
  - AC9 requires the feature to work correctly on both SQLite and
    PostgreSQL; this bug means it does not, on the database Production
    actually uses (Neon Postgres per `CLAUDE.md`).

- Minor: `check_achievements_with_rewards()` runs a full
  `backfill_user_rewards_in_session` scan (re-querying and re-checking
  every unlocked achievement) on **every** `/achievements/check` call, not
  just when needed. Functionally idempotent (once the above race is fixed)
  but is O(unlocked achievements) extra work per check call. Not blocking,
  worth a follow-up if `/check` is called frequently.

## Verdict

**REJECTED**

Reason: the idempotent-crediting implementation does not match its own
ADR and has a real double-credit race on PostgreSQL (the production
database) for the backfill path, which directly violates AC3
("Repeated or concurrent `/achievements/check` calls never double-credit").
This is a money-equivalent correctness bug (Treasure tokens), not a
style nit, so it must be fixed before merge:

1. In `credit_reward_in_session` (`src/services/achievement_rewards.py`),
   move the `CreditTransactionRow` existence check to *after* the
   `CreditBalanceRow` `.with_for_update()` lock is acquired (re-check under
   the lock), so it matches ADR-0020 §2 as written.
2. Add a test that exercises concurrent crediting of a *pre-existing*
   unlocked-but-uncredited achievement (the backfill race), not just
   concurrent first-unlock — ideally against Postgres, or at minimum
   structured so the fix is exercised meaningfully even under SQLite
   (e.g. asserting the code path order via instrumentation) if a Postgres
   CI lane isn't available.

Everything else (tier mapping, API shape, CLI, frontend wiring, docs,
diagrams, README) is solid and can stay as-is once the fix above lands.

## Retrospective Seeds

- **Pattern:** An ADR described the correct lock-then-check ordering for
  idempotent crediting, but the implementation shipped with the check and
  lock reversed, and this passed all tests because the test suite runs on
  SQLite, whose single-writer lock hides the exact race the ADR was
  written to prevent.
  **Role(s) affected:** developer, qa
  **Lesson:** when an ADR specifies a precise operation order for
  concurrency safety (lock-then-check, not check-then-lock), the developer
  should add a code comment or assertion tying the implementation to that
  ADR section, and QA/TechLead should diff the implementation against the
  ADR's stated steps line-by-line rather than trusting that "a
  `with_for_update()` call exists somewhere in the function" is sufficient.
  Concurrency tests that only run on SQLite give false confidence for
  Postgres-specific races — flag this explicitly in test file docstrings
  when a batch can't add a Postgres CI lane.
- **Pattern:** the wave-2-summary and wave-1-summary correctly flagged an
  unrelated pre-existing test failure and cited a "verify against baseline"
  step, but did not actually run the baseline diff to confirm within the
  same run.
  **Role(s) affected:** developer
  **Lesson:** when a summary claims a failure is "pre-existing/unrelated,"
  attach the one-line evidence (e.g. "reproduced on commit X") rather than
  deferring that check to the next role — it costs little and removes
  ambiguity for the reviewer.
