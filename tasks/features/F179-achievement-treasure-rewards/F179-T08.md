## Test scenarios

- Journey: add card → `POST /check` → balance via `GET /credits/balance` = +50;
  `GET /credits/history` contains `achievement_reward`.
- Idempotency: 5 sequential `/check` calls → exactly one ledger row per key.
- Concurrency-ish: threads (ThreadPoolExecutor, 4 workers) calling
  `check_achievements_with_rewards` for the same user on a file SQLite DB →
  ledger rows per key == 1 (tolerate `OperationalError: database is locked`
  retries; assert no double credit).
- Legacy: insert `AchievementRow`s directly (pre-F179), run CLI `--dry-run`
  (no change) → run CLI (credited) → `/check` → `backfilled == 0`.
- Legacy lazy: pre-existing rows, no CLI → `/check` → `backfilled` = expected sum.
- Boundary: user with all achievements (incl. `set_master` via `grant_set_master`) → total 3400.
- Deduction interplay: after reward, `CreditService.deduct(...)` works and ledger sums == balance.
