# F179-T04 — Credit rewards on unlock + lazy backfill + API fields

**Wave:** 1
**Type:** backend
**Depends on:** F179-T02
**Status:** planned

## User Story

As a player, I want to receive Treasure the moment I unlock an achievement (and
for achievements I already had), so that my balance reflects my progress.

## Objective

Integrate `achievement_rewards` into `src/services/achievements.py` (same
transaction as unlock, lazy backfill, reward fields, treasure_hunter fix) and
extend the achievements router responses.

Veja `_brief/00-overview.md`, `_brief/01-reward-model.md` e `_brief/02-backend-integration.md`.

## Implementation details

- `src/services/achievements.py`:
  - `check_achievements_with_rewards(user_id, repo) -> dict` (see `_brief/02`);
    `check_achievements` returns `...["newly_unlocked"]`.
  - Lazy backfill runs even when `earned_keys` is empty.
  - `get_user_achievements` adds `reward`, `tier`, `reward_credited` (single
    `credited_keys()` query).
  - `grant_set_master` credits on rowcount 1.
- `src/api/routers/achievements.py`:
  - `GET ""` items add `reward`, `tier`, `reward_credited`.
  - `POST /check` returns `newly_unlocked`, `rewards`, `total_reward`, `backfilled`, `balance`.

## Acceptance criteria

- [ ] Unlock + credit happen in one commit; ledger row per unlock
- [ ] Calling `/check` twice: second returns `newly_unlocked == []`, `total_reward == 0`, balance unchanged
- [ ] Pre-existing `AchievementRow` without ledger row → credited on next `/check` (`backfilled`)
- [ ] `treasure_hunter` unlocks with 5 `bonus_claim` tx; `achievement_reward` tx never counted
- [ ] `GET /achievements` includes reward fields for locked and unlocked items
- [ ] Existing tests still pass; `ruff check src/` clean

## Test scenarios

- Happy: add 1 card → `/check` → `first_card`, reward 50, balance 50, 1 ledger row.
- Happy: 10 cards → first_card + collector_10 → total 150.
- Happy: `GET` shows `reward_credited=True` only for credited keys; locked keys show reward and `tier`.
- Edge: second `/check` → no rewards, no dup ledger rows.
- Edge: simulate race — insert `AchievementRow` manually between evaluation and insert (or call the in-session path twice) → only one credit, key not in `newly_unlocked` twice.
- Edge: `set_master` row pre-existing, no earned keys → lazy backfill credits 1000.
- Edge: `grant_set_master` twice → credited once (1000).
- Bug fix: 5 `bonus_claim` → treasure_hunter; 4 → not; 5 `achievement_reward` → not.
- Boundary: user with pre-existing balance 0 row vs no balance row.
- Error: unknown achievement key present in DB (legacy) → ignored, `/check` still 200.
- Language: pt-BR user still gets reward fields.
