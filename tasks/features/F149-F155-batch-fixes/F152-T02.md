# F152-T02: Backend — optimize movers query + add timeout

**Feature:** F152 — Dashboard movers timeout fix
**Wave:** 0
**Status:** planned

## User Story

As a user with a large collection, I want the movers panel (alta/baixa)
to load within a few seconds, not time out.

## Root Cause

**NOTE:** `get_movers()` (market-wide) was already fixed in F144 with
ROW_NUMBER CTEs. The **collection-level** movers endpoint at
`GET /collection/movers` uses a DIFFERENT function:
`get_trending_price_data_for_user()` (repository.py:1111).

This function fetches ALL price observations for ALL collection cards
via heavy JOINs (source_cards x price_observations x user_collection),
returns them to Python, then Python iterates to compute changes. With
large collections + dense price history on Neon, this exceeds 10s
(the frontend's DEFAULT_TIMEOUT_MS).

**Frontend already has 10s timeout** via `DEFAULT_TIMEOUT_MS` in
`client.ts`, so no frontend timeout changes needed. The fix is
backend-only: optimize the query.

## Dev Notes

### Approach: SQL-side optimization (same pattern as F144's get_movers)

Replace `get_trending_price_data_for_user` + Python computation in the
`collection_movers()` endpoint with a new optimized repository method
that uses ROW_NUMBER CTEs scoped to the user's collection:

```python

    cutoff = date.today() - timedelta(days=days)

```

This avoids fetching ALL rows to Python — only the top N gainers/losers.

### File: `src/database/repository.py`

Add `get_collection_movers_optimized(user_id, days, limit)` that returns
`(gainers, losers)` directly as tuples with card info included.

### File: `src/api/routers/collection.py`

Update `collection_movers()` endpoint (line 396) to use the new optimized
method instead of `get_trending_price_data_for_user` + Python computation.
Keep `investment_only` filter working (add acquisition_price join in CTE).

### Timeout guard

Add `statement_timeout` for the query as a safety net:
```python
session.execute(text("SET LOCAL statement_timeout = '10s'"))
```
