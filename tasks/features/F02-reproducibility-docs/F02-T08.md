## User Story

As the project architect, I want to record the web framework decision as an ADR
so that future contributors understand why we chose a specific framework and
what alternatives were considered.

## Objective

Create `docs/adr/0002-web-stack-decision.md` following the ADR template,
documenting the decision to use FastAPI as the web framework for the planned
REST API.

## Dev Notes

- FastAPI is the recommended choice given:
  - Already async codebase (curl_cffi, pytest-asyncio)
  - Automatic OpenAPI docs (important for a data API)
  - Pydantic validation aligns well with domain models
  - Good SQLAlchemy integration
- Alternatives to document: Flask, Django REST Framework, Litestar
- Status should be "proposed" (not "accepted") since the API is not yet built
- Follow the format of ADR-0001 (`docs/adr/0001-adopt-claude-didio-framework.md`)

## Implementation Details

### docs/adr/0002-web-stack-decision.md

Structure (following existing ADR format):

```markdown
# ADR-0002: Use FastAPI for REST API

**Status:** proposed
**Date:** 2026-08-18
**Deciders:** Eduardo Rutkoski Didio

## Context
[Why we need a web framework, what the API will serve]

## Decision
[Choose FastAPI, reasons: async-first, OpenAPI auto-docs, Pydantic,
SQLAlchemy integration, community size]

## Consequences
**Easier:**
- Async handlers match existing async provider code
- Auto-generated OpenAPI/Swagger docs
- Pydantic models can share structure with domain dataclasses
- Large ecosystem of middleware (CORS, auth, rate limiting)

**Harder:**
- Adds dependency (fastapi, uvicorn)
- Team must learn FastAPI patterns if unfamiliar
- Pydantic v2 migration considerations

## Alternatives considered
- Flask -- mature, simpler, but sync-first
- Django REST Framework -- batteries-included but heavy for this project
- Litestar -- modern async alternative, smaller community
- No framework (raw ASGI) -- too much boilerplate
```
