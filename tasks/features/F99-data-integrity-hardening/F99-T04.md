# F99-T04 -- FK Constraints Migration

**Wave:** 1 (parallel with T03, T05)
**Depends on:** T01 (orphan cleanup must run first)

## User Story

As a developer, I want the database schema to declare foreign key
relationships so that referential integrity is enforced by the database
engine, not just by application logic.

## Problem

All `card_id`, `deck_id`, `user_id` references in the schema are plain
`Integer` columns with no `ForeignKey` declaration. SQLAlchemy models
do not express these relationships, so the database cannot enforce them.

**Note on user_id types:** `UserCollectionRow.user_id`, `DeckRow.user_id`,
`PortfolioSnapshotRow.user_id`, and `ScheduledScanRow.user_id` are
`String(100)` but `UserRow.id` is `Integer`. These cannot have a direct
FK constraint until the type mismatch is resolved. **Do NOT add FK
constraints on string user_id columns in this task.** Document this as
technical debt for a future migration.

### SQLite migration strategy

SQLite does not support `ALTER TABLE ADD CONSTRAINT`. The standard
migration pattern is:

1. `ALTER TABLE source_cards RENAME TO _source_cards_old`
2. `CREATE TABLE source_cards (... card_id INTEGER REFERENCES cards(id) ON DELETE SET NULL ...)`
3. `INSERT INTO source_cards SELECT * FROM _source_cards_old`
4. `DROP TABLE _source_cards_old`

However, since we use `Base.metadata.create_all` with the updated model
definitions, and T01 has already cleaned orphans, we can use a simpler
approach:

1. Update the SQLAlchemy model to include `ForeignKey(...)` in the
   `mapped_column` definition
2. In `_ensure_columns` (or a new `_ensure_fk_constraints` method),
   detect if the existing table lacks the FK and perform the table-rebuild
   migration only when needed
3. Use `PRAGMA table_info` and `PRAGMA foreign_key_list` to detect
   current state

### Model changes (example for SourceCardRow)

```python
# Before
card_id: Mapped[int | None] = mapped_column(Integer)

# After
card_id: Mapped[int | None] = mapped_column(
    Integer, ForeignKey("cards.id", ondelete="SET NULL")
)
```

### Migration safety

- Run `PRAGMA foreign_key_check` after migration to verify no violations
- The migration method should be idempotent (skip if FK already exists)
- Create a backup before the table-rebuild operations
- Wrap the entire migration in a transaction

### Tables NOT getting FK constraints (documented debt)

- `user_collection.user_id` (String -> Integer type mismatch)
- `decks.user_id` (String -> Integer type mismatch)
- `portfolio_snapshots.user_id` (String -> Integer type mismatch)
- `scheduled_scans.user_id` (String -> Integer type mismatch)

## Testing

- Unit test: create a fresh DB, verify FK constraints exist via
  `PRAGMA foreign_key_list(table_name)`
- Unit test: migrate an existing DB (no FKs), verify FKs are added
- Unit test: run migration twice (idempotent -- no error on second run)
- Unit test: after migration, inserting invalid FK raises IntegrityError
  (requires T03 PRAGMA to be active)
- Unit test: `PRAGMA foreign_key_check` returns empty after migration
