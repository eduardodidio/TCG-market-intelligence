# F99-T06 -- Atomic Transaction Wrapper for Sync Pipeline

**Wave:** 2 (parallel with T07)
**Depends on:** T03, T04 (FK constraints must be in place)

## User Story

As a user, I want collection sync to either fully succeed or fully roll
back for each card so that my database never has partial/inconsistent
state from a failed sync.

## Problem

In `sync_collection.py`, `_process_single_entry` calls multiple repo
methods sequentially (steps 3b through 3g), each opening its own session.
If step 3e (insert observations) succeeds but step 3f (link entry) fails,
the database has observations for an unlinked card -- an inconsistent
state that is hard to recover from.

## Dev Notes

### Scope of the transaction

The transaction should wrap the **database mutation** steps only:

- 3b: `repo.upsert_card(detailed)` -- returns card_id
- 3c: `repo.upsert_source_card(detailed, card_id=card_id)`
- 3e: `repo.insert_price_observations(history)`
- 3f: `repo.link_collection_entry(row.id, card_id)`
- 3g: `repo.mark_errors_resolved("myp", source_card.external_id)`

The **external API calls** (steps 1, 3a, 3d) MUST NOT be inside the
transaction -- they are slow, may timeout, and should not hold a DB lock.

### Implementation approach

Add a new repository method that accepts a session and performs all
mutations within it:

```python
def sync_card_atomic(
    self,
    session: Session,
    detailed: CardDetails,
    card_id_hint: int | None,
    observations: list[PriceObservation],
    entry_id: int,
    source: str,
    external_id: str,
) -> tuple[int, int]:
    """Atomically upsert card, source_card, observations, link, resolve errors.
    Returns (card_id, observations_inserted).
    """
```

Alternatively, add a context manager to Repository that yields a session:

```python
@contextmanager
def transaction(self):
    with Session(self.engine) as session:
        try:
            yield session
            session.commit()
        except Exception:
            session.rollback()
            raise
```

Then refactor `_process_single_entry` to use it:

```python
with repo.transaction() as session:
    card_id = repo.upsert_card(detailed, session=session)
    repo.upsert_source_card(detailed, card_id=card_id, session=session)
    inserted = repo.insert_price_observations(history, session=session)
    repo.link_collection_entry(row.id, card_id, session=session)
    repo.mark_errors_resolved(source, external_id, session=session)
```

### Key decision: session-passing vs. new method

The context manager + session-passing approach is preferred because:
- It does not duplicate logic
- It makes the transaction boundary explicit in the caller
- Existing non-transactional callers continue to work unchanged

Each repo method that participates needs an optional `session` parameter.
When provided, it uses the external session; when not, it creates its own
(backward compatible).

### Concurrency note

The sync pipeline uses `asyncio.Semaphore(concurrency)` with default
concurrency=3. SQLite allows only one writer at a time. The transaction
wrapper should be quick (no network I/O inside), so writer contention
should be minimal. No changes to concurrency logic needed.

## Testing

- Unit test: successful sync -- all 5 mutations committed atomically
- Unit test: failure in step 3f (link entry) -- verify steps 3b, 3c, 3e
  are rolled back (no card, no source_card, no observations in DB)
- Unit test: failure in step 3e (insert observations) -- verify upsert_card
  is rolled back
- Unit test: transaction context manager rolls back on exception and
  re-raises
- Unit test: repo methods still work without explicit session (backward
  compat)
