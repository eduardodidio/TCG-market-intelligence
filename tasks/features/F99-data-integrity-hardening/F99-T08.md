# F99-T08 -- Collection Deletion Cascade (SET NULL on deck_cards)

**Wave:** 3 (parallel with T09)
**Depends on:** T04 (FK constraints in place)

## User Story

As a user, when I delete a card from my collection, I want my deck lists
to keep the card entry (so the deck is not silently broken) but lose the
link to the canonical card (since I no longer own it).

## Problem

`Repository.delete_collection_entry()` (line 996) deletes the
`UserCollectionRow` but does NOT handle dependent rows:

- `DeckCardRow.card_id` may reference the same canonical card. After the
  collection entry is deleted, the deck card still shows "owned" because
  `card_id` is still set. This is semantically wrong but not a crash.
- With FK constraints from T04, deleting a collection entry does not
  directly cascade to deck_cards (there is no FK from deck_cards to
  user_collection -- the FK is deck_cards.card_id -> cards.id). So the
  deck card link survives correctly at the DB level.

However, the **application-level** concern is:
When a user deletes a collection entry, the ownership overlay on deck
views should reflect the card is no longer owned. The current
`get_deck_cards_with_ownership` already handles this correctly via a
live JOIN to user_collection. So no data change is needed for deck
display.

### What DOES need fixing

The `delete_collection_entry` and `bulk_delete_collection_entries` methods
should handle cleanup of related data:

1. **EvaluationEntryRow** -- if an evaluation entry was promoted to this
   collection entry and shares the same card_id, it should have its
   card_id SET NULL (handled by T04 FK cascade on cards.id, not directly).

2. **Price observations** -- when deleting a collection entry, we should
   NOT delete price history (it belongs to the card, not the collection
   entry). This is already correct behavior.

3. **PortfolioSnapshotRow** -- stale snapshots may reference counts that
   include the deleted card. These should be recalculated lazily (on next
   snapshot) rather than eagerly cleaned up.

### Bulk delete cascade

The `bulk_delete_collection_entries` method (if it exists) should follow
the same pattern. Verify it exists and handles the same concerns.

### Implementation

1. Review `delete_collection_entry` -- confirm it does not need to cascade
   to any additional tables beyond what T04 FK constraints handle.
2. Add a post-delete step: if the deleted entry's `card_id` is not
   referenced by any other `UserCollectionRow`, and it has no
   `SourceCardRow` linked to it, log a warning that the card is now
   orphaned (but do NOT delete it -- the card data is still valuable for
   price history and may be re-added).
3. Ensure `bulk_delete_collection_entries` (batch edit delete) follows
   the same logic.

### DeckCardRow.card_id on card deletion

If a `CardRow` is ever deleted (via cleanup.py), the FK constraint
`deck_cards.card_id -> cards.id ON DELETE SET NULL` (from T04) ensures
deck cards lose their link but are not deleted. Verify this cascade
works correctly.

## Testing

- Unit test: delete collection entry -- verify deck_cards with same
  card_id still exist, card_id still set (no cascade from collection
  to deck)
- Unit test: delete a CardRow -- verify DeckCardRow.card_id is SET NULL
  (FK cascade from T04)
- Unit test: delete collection entry -- verify price observations for
  that card still exist
- Unit test: bulk delete collection entries -- same cascading behavior
- Unit test: delete collection entry -- `get_deck_cards_with_ownership`
  correctly shows card as not owned
