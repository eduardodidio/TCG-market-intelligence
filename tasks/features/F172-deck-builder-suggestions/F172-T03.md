## User Story

As a player, I want my deck-suggestion request stored safely, so that it can be processed later and I can track its status.

## Objective

Create the ORM row in its own module plus the queue functions (create, list, get, claim, done, failed, retry, save link).

## Dev Notes

See `_brief/00-overview.md` and `_brief/02-suggestion-persistence-api.md` (table + repository sections — follow them exactly).

- `from src.database.models import Base`. **Do not edit `src/database/models.py`** (batch-conflict rule).
- The table is created via `DeckSuggestionRequestRow.__table__.create(engine, checkfirst=True)` inside `ensure_table`,
  memoized with a module-level `set[int]` of `id(engine)`. `Base.metadata.create_all` in `Repository.__init__` will ALSO
  create it once this module has been imported. Both paths are idempotent.
- The FKs point to `cards.id` and `decks.id`. `ensure_table` must run after those tables exist (in practice `Repository(...)` has already run).
  Tests: build `Repository("sqlite:///:memory:")` first, then call the functions with `repo.engine`.
- Pattern reference: `PriceUpdateRequestRow` (`src/database/models.py:602`) and `repo.get_pending_price_requests`.
- Claim atomically: `update(Row).where(Row.id == id, Row.status == old_status).values(...)` and check `result.rowcount == 1`.
- Return detached objects: `Session(engine, expire_on_commit=False)`.
- `colors` are stored as a string in WUBRG order (`"WU"`), and the API converts to/from a list. Provide helpers `colors_to_str(list) -> str | None`
  and `colors_from_str(str | None) -> list[str]` in `repository.py`.

## Implementation details

- `src/deck_suggestions/models.py`: `DeckSuggestionRequestRow` as specified.
- `src/deck_suggestions/repository.py`: `ensure_table`, `create_request`, `count_open_requests`, `list_requests`,

## Acceptance criteria

- [ ] The table is created on SQLite without touching `models.py`. Calling `ensure_table` twice is a no-op.
- [ ] `claim_pending` never returns the same row twice across two sequential calls, and it re-claims `processing` rows older than `stale_after`.
- [ ] Ownership: `get_request` / `delete_pending_request` return None/False for another user's row.
- [ ] `mark_done` stores UTF-8 JSON (`ensure_ascii=False`) and `load_result` round-trips it.
- [ ] 100% line coverage of `repository.py`.

## Test scenarios

- Happy: create → list (newest first) → get → claim (status processing, attempts 1) → mark_done → load_result.
- Edge: `list_requests(status="done")` filter; `limit` respected; `count_open_requests` counts pending + processing only.
- Error: `delete_pending_request` on a processing row → False; `load_result` with corrupt JSON → None; mark_failed truncates to 1000 chars.
- Boundary: claim with `limit=0` → `[]`; a stale processing row exactly at the threshold isn't re-claimed, and one just past it is; `release_for_retry` → back to pending, attempts kept.
- Concurrency sim: two claims where the second sees status already changed (simulate by updating between select and update) → not returned.
