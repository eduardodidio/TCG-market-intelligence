# F172-T18 — i18n (shared files): `deckBuild.*` + `deckSuggest.*` in en / pt-BR

- **Wave:** 4
- **Type:** frontend
- **Depends on:** F172-T06, F172-T10, F172-T11, F172-T12, F172-T13, F172-T14
- **Status:** planned

## User Story

As a Brazilian player, I want the deck builder and the suggestion screens in Portuguese, so that the app feels native.

## Objective

Add every i18n key used by the wizard (`deckBuild.*`, missing today, defect H9) and by the new components (`deckSuggest.*`) to both locale files.

## Dev Notes

See `_brief/00-overview.md`, `_brief/01-commander-search-fix.md` (H9) and `_brief/05-integration-docs.md`.

- Locales: `frontend/src/i18n/locales/en.json`, `frontend/src/i18n/locales/pt-BR.json`. There is an existing `deckBuilder` object (~L451 pt-BR). **Do not rename it.**
  Add new sibling objects `deckBuild` and `deckSuggest`.
- Collect the keys with: `grep -rhoE "t\(\"(deckBuild|deckSuggest)\.[A-Za-z0-9_.]+\"" frontend/src | sort -u`.
  The English value = the `defaultValue` in the code. pt-BR = a natural translation. The project uses gaucho flavor in some strings (F54). Keep it neutral here unless the neighbors do otherwise.
- **Batch conflict rule:** other F171–F179 features may edit these JSON files. Insert the new top-level keys (don't reorder existing ones) and keep the formatting (2-space indent).
- If there is an i18n key-parity test (`frontend/src/i18n/__tests__/`), it must pass. Read it first.

## Implementation details

Both files get identical key sets for `deckBuild` and `deckSuggest` (nested: `deckSuggest.mode.*`, `.form.*`, `.list.*`, `.status.*`, `.result.*`).

## Acceptance criteria

- [ ] Every `deckBuild.*` / `deckSuggest.*` key used in `frontend/src` exists in both files.
- [ ] Both JSON files are valid, and the existing i18n tests pass.
- [ ] `npm test` and `npm run build` are green.

## Testing

`cd frontend && npx vitest run src/i18n` and then `npm test`. Add a small test `src/i18n/__tests__/deckSuggestKeys.test.ts` that loads both JSON files and asserts
the `deckBuild` / `deckSuggest` key sets are equal and non-empty (skip it if a generic parity test already covers all namespaces).

## Test scenarios

- Happy: key parity en ↔ pt-BR.
- Edge: nested keys (`deckSuggest.status.pending`) are present.
- Error: a missing key in pt-BR → the test fails (verify by temporarily removing one key locally, then restore it).
- Boundary: interpolation placeholders (`{{query}}`) are identical in both languages.
