## Wave 1 — F177-T03, F177-T04, F177-T05

**Architecture:** `src/database/legality_writer.py` and
`src/database/banlist_queries.py` are new, pure modules — no edits to
`models.py`/`repository.py`, matching the "files not touched" constraint.
Layering respected: writer does chunked upserts via `dialect_insert`
(Postgres/SQLite portable), queries module is read-only and dialect-agnostic
(`sqlalchemy.select`, no raw SQL).

**Code quality:**
- `legality_writer.bulk_upsert_legalities` dedupes `(card_id, format)` within
  a chunk before the `ON CONFLICT` statement (correctly avoids Postgres's
  "cannot affect row a second time" error) and preserves a non-null
  `effective_date` via `func.coalesce(excluded.effective_date, ...)` — a
  detail that's easy to get wrong and is handled correctly.
- `banlist_queries.list_banlist_grouped` groups in Python after a single SQL
  fetch (no N+1), and correctly short-circuits `owned_only=True` with no
  `user_id` to `([], 0)` rather than raising — appropriate defensive default
  for the unauthenticated case (though the router itself already 401s before
  reaching this branch, so this is a second line of defense, not dead code —
  it also protects any future caller of the module).
- Representative-printing / group-status logic (owned printing wins, else
  lowest `card_id`; status severity `banned > restricted`) is a reasonable,
  documented tie-break.

**Test coverage:** `test_legality_writer.py` (248 lines) and
`test_banlist_queries.py` (340 lines) cover happy path, dedup, coalesce,
grouping, owned-filter, pagination boundaries per the Wave-1 summary.
`BanCardDetailModal.test.tsx` (205 lines) covers the component in isolation
with mocked `api/banlist`.

**Cross-task consistency:** T04's Dev Notes flagged a deliberate forward-
compat choice — reading `printings/owned/owned_quantity` via a local
`ModalEntry` type since T08 hadn't extended `BanListEntry` yet. By Wave 2,
T08 did extend `BanListEntry` with exactly those fields
(`frontend/src/types/banlist.ts`), and `BanCardDetailModal.tsx`'s `ModalEntry
= BanListEntry & Partial<{...}>` still works against the now-widened type —
no drift.

## Wave 2 — F177-T06, F177-T07, F177-T08

**Architecture:** `src/collectors/banlist_sync.py` stays a pure orchestrator
that delegates writes to `legality_writer` — no direct DB writes outside that
module. `src/api/routers/banlist.py`'s `GET /banlist` now calls
`banlist_queries.list_banlist_grouped` instead of ad hoc repository logic;
`GET /banlist/status` is new and thin (schema mapping only). Good separation.

**Code quality / correctness (verified by re-reading the sync rewrite):**
- Redirect-following: `httpx.AsyncClient(follow_redirects=True)` — fixes
  RC1 from the diagnosis.
- `_select_download_url` prefers `jsonl_download_uri` over `download_uri`
  — fixes the "only reads the JSON-array bulk URL" bug.
- `_iter_bulk_lines` handles both `.gz`-suffixed URLs and gzip-magic-byte
  sniffing on the first chunk (covers a redirected URL that drops the `.gz`
  suffix) — good defensive detail.
- `_build_index_keys` builds a key set covering raw/mapped set codes ×
  raw/zero-stripped collector numbers, so both RC2 (Liga-style set codes)
  and RC-adjacent (zero-padded collector numbers) match cases are covered.
- `_classify`'s compact-scope logic (`should_store`) matches AC4 exactly:
  banned/restricted, or owned, or previously-existing. First-sync baseline
  rows get `source="scryfall_baseline"` with `effective_date=None`;
  transitions get `source="scryfall_sync"` with `effective_date=today()`.
  Re-running with unchanged data hits `existing == status` → `(False, None,
  None)` → 0 writes, 0 history (AC3), confirmed by
  `test_second_run_no_changes_zero_upserts_zero_history`.
- Fail-loud behavior (AC5) is implemented exactly as scoped in the ADR
  (0 lines parsed → always raises; 0 matches → raises only past
  `MATCH_CHECK_THRESHOLD=1000` lines, to avoid false positives on small/dev
  runs) — see Wave 0 note above. Not a defect since the PRD/ADR/T06 AC text
  all agree on this refined behavior, but it does mean the *README's* AC5
  wording is imprecise; worth tightening the README wording in a future pass
  so it doesn't read as a stricter guarantee than what's implemented.

**Test coverage:** `test_sync_f177.py` covers redirect/gzip/plain,
zero-matches-over-threshold, zero-lines, limit capping, and the
no-op-second-run case — all with `httpx.MockTransport`, no live network calls
(appropriate for CI/sandbox). `test_api_f177.py` (250 lines) covers grouped
shape, `owned_only` + 401, and `/status`.

**API/schema consistency:** `BanListEntry` (schema) matches what
`list_banlist_grouped` returns (`printings`, `owned`, `owned_quantity`,
`effective_date`) and what the frontend `types/banlist.ts` / `BanList.tsx`
consume (`entry.printings`, `entry.owned`, `entry.owned_quantity`,
`entry.effective_date`) — verified field names line up on both sides of the
HTTP boundary.

finished code/tests — corrected during this review.

## Retrospective Seeds

- **Pattern:** Multiple task files (T02, T08, T10 this feature; called out by
  the developer themselves in two of three cases) shipped code+tests but left
  `Status: planned` in the header.
  **Role(s) affected:** developer
  **Lesson:** Flip the task file's `Status:` field to `done` as the last step
  of implementing a task, not as an afterthought — TechLead had to patch three
  files before sign-off this time.

- **Pattern:** A Wave-3 summary asserted several frontend test failures were
  "pre-existing... confirmed via git stash" without showing the confirmation.
  TechLead independently re-derived the same conclusion by diffing
  `Layout.tsx`/`Layout.test.tsx` against the pre-Wave-3 commit, which took
  real effort given the file was a declared hotspot.
  **Role(s) affected:** developer, techlead
  **Lesson:** When a developer claims "pre-existing failure, unrelated to my
  change," attach the actual `git stash`/before-after diff or command output
  to the wave summary — it turns a one-line claim TechLead must re-verify
  from scratch into a checkable fact.

- **Pattern:** The README-level global AC list (F177-README.md AC5) is a
  simplified restatement of a nuance ("threshold" for the zero-match check)
  that the PRD and ADR spell out precisely. Anyone reading only the README
  would flag a false discrepancy.
  **Role(s) affected:** architect
  **Lesson:** When an AC in the README manifest has been intentionally
  narrowed/qualified in the PRD, either update the README AC's wording during
  Wave 0, or add a one-line pointer ("see PRD for exact threshold") so
  reviewers don't have to hunt for the refinement.

- **Pattern:** The full backend suite currently has 112 pre-existing failing
  tests (Liga URL builder, marketplace repository, deck/collection
  repository, currency, liga-relink/coverage) unrelated to any single
  in-flight feature — almost certainly batch-merge fallout across
  concurrently-run F171–F179 worktrees.
  **Role(s) affected:** architect, qa (batch owner)
  **Lesson:** This is outside F177's blast radius (verified: zero overlap
  with F177's touched files) so it doesn't block this feature, but it should
  be triaged as its own cleanup item before the F171–F179 batch reaches
  `main` — otherwise "pytest tests/ green" stops being a meaningful gate for
  every subsequent feature in the batch.

Verdict: APPROVED_WITH_FOLLOWUP
