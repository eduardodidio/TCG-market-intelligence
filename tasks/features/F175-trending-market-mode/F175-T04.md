# F175-T04 — TrendingService does not cache failures

- **Wave:** 1
- **Type:** backend
- **Depends on:** F175-T01
- **Status:** planned

## User Story
As a user, I want a transient DB timeout to not freeze Tendências empty for 30 minutes, so that a reload shows data as soon as the database answers.

## Objective
In `TrendingService.get_trending`, do not store the response in the cache when the query raised an
exception. Use a short TTL (2 min) for an empty but legitimate result. Add the structured log `trending_computed`.

## Dev Notes
Veja `_brief/00-overview.md` e `_brief/03-service-cache.md`.
- File: `src/services/trending.py` (the service is a singleton in `src/api/routers/market.py:56-63`).
- Logging: `structlog` (`log.info("trending_computed", ...)`) as already used in the file.
- F165 guarantee: the router never returns 500. Keep the broad `except Exception` and the empty response.
- Do not change the signatures of `get_trending` / `invalidate_cache` / `_apply_currency`.

## Implementation details
- Track `query_failed`. Skip `self._cache[...] = ...` when it is `True`.
- Store the TTL per entry, or check `cards == []` on read with `self._empty_cache_ttl = timedelta(minutes=2)`.
- Log `trending_computed` with scope, direction, period_days, cards_with_prices, ranked.

## Acceptance criteria
- [ ] Repo raising an exception → empty response, and a 2nd call calls the repo again (mock `call_count == 2`).
- [ ] Legitimate empty result → cached for ≤ 2 min; recomputed after that.
- [ ] Non-empty result → cached for 30 min (current behavior).
- [ ] Existing tests pass: `tests/unit/services/test_trending_service.py`, `tests/test_trending_error_resilience.py`, `tests/unit/services/test_trending_collection_only.py`.

## Test scenarios
- Happy: success with cards → 2nd call served from cache (`cached=True`).
- Error: `OperationalError`/`RuntimeError` on the 1st call → no cache; the 2nd call succeeds and returns cards.
- Edge: legitimate empty result → cached; after 2 min + 1 s → recomputed.
- Boundary: exactly 30 min vs 29:59 for a non-empty result.
- Isolation: a failure in `scope=all` does not affect the `user_{id}` cache, and the reverse.
