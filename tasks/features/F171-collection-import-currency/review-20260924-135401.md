## T09 — `batch_add.py` BRL storage

- Wiring (`BatchAddEntry.acquisition_price`/`price_currency` → `to_brl` → `UserCollectionRow`) is
  correct and matches the pydantic schema constraints (`ge=0, le=1_000_000`,
  `Literal["BRL","USD"]`).
- Good catch documented in the Wave 3 summary: fixed a **real latent bug** — the per-entry
  `session.begin_nested()` savepoint was never committed on the success path, which would blow the
  recursion limit on large batches. The fix (`savepoint.commit()` at `batch_add.py:112`) is a
  one-line, low-risk change inside a file this task already owned.
- **IMPORTANT finding (not blocking, no live caller triggers it today):**
  `batch_add.py:82-96` gates the *entire* conversion path on `rate_lookup is None`, before ever
  checking the entry's currency:
  ```python
  if entry.acquisition_price is not None:
      if rate_lookup is None:
          result.warnings.append(f"{entry.name_en}: no exchange rate available, price not stored")
      else:
          conversion = to_brl(entry.acquisition_price, entry.price_currency or "BRL", ...)
  ```
  `to_brl` itself never needs a rate for BRL (it short-circuits and returns the amount
  unconverted). So a caller that passes `rate_lookup=None` together with a **BRL** priced entry
  will silently drop a price that needed no conversion at all, and emit a misleading "no exchange
  rate available" warning for a currency where no rate was ever required. Today's only caller that
  sets `acquisition_price` (`POST /collection/batch` in `collection.py:1790`) always passes a real
  `rate_lookup`, so this is not user-visible yet, but it's an inconsistency with `to_brl`'s own
  contract ("BRL never needs a rate") and a foot-gun for the next caller (e.g. a future CLI batch
  command). No test exercises `batch_add_entries(..., rate_lookup=None)` with a BRL price.
  **Suggested fix:** call `to_brl` unconditionally with a `rate_lookup or (lambda _d: None)`
  fallback (same pattern already used in `importer.py:113`), instead of branching on
  `rate_lookup is None` before the currency is even known.
- Tests: `tests/api/test_collection_batch_currency.py` — 11 tests covering parse, conversion,
  BRL-unchanged, None-as-BRL, no-rate-warning, zero/negative price, unsupported currency, old

## Retrospective Seeds

- **Pattern:** Several waves (1, 2, 3, 4) shipped their diffs without committing, and the Wave
  summaries themselves had to flag "confirm commit strategy with the orchestrator" repeatedly.
  **Role(s) affected:** developer, architect. **Lesson:** the Architect's Wave plan should state
  explicitly whether each Wave commits before the next one starts, so developers don't have to
  improvise and Tech Lead doesn't have to reconstruct wave boundaries from uncommitted working-tree
  state.
- **Pattern:** A conversion helper (`to_brl`) that "doesn't need a rate for BRL" got re-guarded
  behind a `rate_lookup is None` check one layer up in `batch_add.py`, undoing that invariant for
  one call site. **Role(s) affected:** developer, techlead. **Lesson:** when a pure function
  already encodes a short-circuit invariant (e.g. "BRL never needs a rate"), don't re-check the
  precondition for the whole call above it — pass a no-op fallback and let the pure function's own
  branching do the work, the way `importer.py` already does (`rate_lookup or (lambda _d: None)`).
- **Pattern:** Wave 2 and Wave 3 summaries both independently found and correctly diagnosed
  pre-existing test failures via `git stash`/base-commit comparison instead of blocking their own
  wave on unrelated flakiness. **Role(s) affected:** developer. **Lesson:** this is the right
  instinct — a future project-wide task should actually fix the 13 pre-existing frontend failures
  and 5 backend failures identified across F171's waves, since they've now been rediscovered and
  reverified three times across this one feature.
