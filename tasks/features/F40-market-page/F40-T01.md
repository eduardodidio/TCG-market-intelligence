# F40-T01 -- Backend: Market Summary + Volatile Endpoints

**Wave:** 0
**Depends on:** None (within F40). Requires F36 TrendingService to exist
for volatile endpoint; degrades gracefully if absent.
**Produces:** Two new API endpoints consumed by all frontend tasks.

## Objective

Add `GET /market/summary` and `GET /market/volatile` endpoints to the
existing `market.py` router. These are thin aggregation layers over
existing repository queries and (optionally) the F36 trending service.

## Deliverables

### 1. Pydantic Schemas (`src/api/schemas/market_summary.py`)

New file with:

```python
class MarketSummaryResponse(BaseModel):
    total_cards_tracked: int
    total_observations: int
    avg_price: float | None
    avg_price_change_pct: float | None
    gainers_count: int
    losers_count: int
    unchanged_count: int
    market_direction: str  # "up" | "down" | "flat"
    period: str
    currency: str
    computed_at: datetime
```

The volatile endpoint reuses `TrendingCardEntry` from F36's
`src/api/schemas/trending.py`. If F36 schemas do not exist yet, define a
minimal `VolatileCardEntry` locally with the same fields.

### 2. Market Summary Endpoint

Add to `src/api/routers/market.py`:

```
GET /market/summary?period=30d&currency=BRL
```

Implementation steps:
1. Validate period against `MOVERS_PERIOD_MAP`.
2. Call `repo.get_market_stats()` for total cards/observations/avg price.
3. Call `repo.get_movers(days, limit=9999)` to get ALL gainers and losers
   (or use trending service batch data if F36 is available).
4. Count gainers (change > 0), losers (change < 0), unchanged (change == 0).
5. Compute `avg_price_change_pct` as mean of all change percentages.
6. Set `market_direction`: "up" if gainers > losers, "down" if losers >
   gainers, "flat" otherwise.
7. Apply currency conversion to `avg_price`.
8. Cache result in a module-level dict with 30-minute TTL (key:
   `f"summary:{period}:{currency}"`). Check cache before computing.

### 3. Most Volatile Endpoint

Add to `src/api/routers/market.py`:

```
GET /market/volatile?period=30d&limit=10&currency=BRL
```

Implementation steps:
1. Try to import and use `TrendingService` from F36.
2. If F36 is available:
   a. Get trending gainers AND losers for the period.
   b. Merge both lists.
   c. Re-rank by volatility score: `|change_pct| * (1 - consistency)`.
   d. Return top `limit` entries.
3. If F36 is NOT available (ImportError or service not wired):
   a. Fall back to `repo.get_movers()`.
   b. Return movers sorted by absolute `|change_pct|` (no consistency
      data available in fallback mode).
4. Apply currency conversion.
5. Cache with same 30-minute TTL pattern.

### 4. Wire to Router

Both endpoints use existing FastAPI dependencies:
- `get_db` for Repository
- `get_currency_converter_dep` for CurrencyConverter
- No authentication required (public endpoints).

Register the response models with `response_model=ApiResponse[...]`.

## Constraints

- Do NOT import from database layer in schemas.
- Do NOT add new database tables or columns.
- Use `Decimal` arithmetic internally, `float` in Pydantic schemas.
- Graceful degradation: if F36 TrendingService is not importable, the
  volatile endpoint still works with movers fallback.
- Cache is process-level dict with TTL, NOT a new dependency.

## Acceptance Criteria

- [ ] `GET /market/summary?period=30d` returns all fields in schema
- [ ] `GET /market/summary?period=7d&currency=USD` applies conversion
- [ ] `GET /market/volatile?period=30d&limit=10` returns ranked cards
- [ ] Volatile endpoint works even if F36 is not shipped (fallback)
- [ ] Invalid period returns 422
- [ ] Results cached for 30 minutes
- [ ] No N+1 queries for summary computation
