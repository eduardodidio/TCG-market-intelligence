# F131-T04 — Catalog Search Coherence Review

## User Story

As a catalog browser, I want search to find cards reliably by either
their English or Portuguese name so that I do not miss results due to
partial matching quirks or encoding issues.

## Dev Notes

### Context

The catalog search uses a LIKE query:
```sql
(c.name_en LIKE :name OR c.name_pt LIKE :name)
```
with `params["name"] = f"%{name}%"`. This is a substring match, which
is correct for basic queries. However, several coherence concerns should
be reviewed:

1. **Case sensitivity** — SQLite LIKE is case-insensitive for ASCII but
   case-sensitive for non-ASCII (accented characters common in
   Portuguese: "Anjo" vs "anjo" works, but "Dragao" vs "dragao" may
   not). PostgreSQL LIKE is always case-sensitive. The production
   database is Neon PostgreSQL, so searching "lightning" will NOT match
   "Lightning Bolt".
2. **Accent handling** — Portuguese names include accents (e.g.,
   "Relampago" vs "Relampago"). Users may type without accents.
3. **Double-faced card names** — DFC cards store the full name as
   "Front Face // Back Face". Searching for "Back Face" alone should
   still match.
4. **Empty result states** — the `EmptyState` component already handles
   filtered vs unfiltered empty states, but the messaging could be
   improved to suggest trying the other language.
5. **Search debounce** — `useCatalogCards` already debounces the name
   filter at 300ms via `useDebounce`. This is fine.

### Implementation Steps

**Backend: `src/api/routers/catalog.py`**

1. **Case-insensitive search**: Replace `LIKE` with `ILIKE` for
   PostgreSQL, or use `LOWER()` wrapping for cross-dialect support:
   ```sql
   (LOWER(c.name_en) LIKE LOWER(:name) OR LOWER(c.name_pt) LIKE LOWER(:name))
   ```
   This ensures "lightning" matches "Lightning Bolt" on both SQLite and
   PostgreSQL.
2. Use `from src.database.compat import is_sqlite` to check dialect if
   a dialect-specific approach is preferred (ILIKE on PG, LIKE on
   SQLite).

**Frontend: `frontend/src/pages/CatalogPage.tsx`**

3. **Improved empty state messaging**: When the search returns 0 results
   and a name filter is active, the empty state description should
   suggest trying the other language. For example:
   - PT: "Tente buscar pelo nome em ingles"
   - EN: "Try searching by the Portuguese name"
   Add i18n keys `catalog.emptySearchHintEn` and
   `catalog.emptySearchHintPt`.

4. **Placeholder text**: Verify the search placeholder mentions both
   languages (e.g., "Search by English or Portuguese name...").

### Key Decisions

- Use `LOWER()` wrapping instead of `ILIKE` for cross-dialect
  compatibility (SQLite local dev + PostgreSQL production).
- Accent-insensitive search (unaccent) is out of scope for this task.
  PostgreSQL's `unaccent` extension would need to be enabled on Neon,
  and the benefit is marginal for this user base. Can be added later.
- The DFC name format ("Front // Back") already works with substring
  LIKE, so no change needed there.
