# F52-T02 — Cache Invalidation on Scan Completion

**Status:** planned
**Wave:** 0
**Estimate:** small

## User Story

As a user who just ran a price scan, I want the trending section to
reflect the latest data immediately, so I don't see stale results for
up to 30 minutes after new prices are collected.

## Dev Notes

### What to change

**`src/services/trending.py`:**
- The `TrendingService` has a 30-minute cache keyed on
  `{direction}:{period_days}`. After a scan completes and new prices
  are stored, the cache is stale but not invalidated.
- `invalidate_cache()` method already exists — just needs to be called.

**`src/services/scan_hooks.py` or `src/collectors/scan.py`:**
- After a scan run completes (ScanRun status → "completed"), call
  `trending_service.invalidate_cache()`.
- The `ScanHookRegistry` from F44 is designed exactly for this — register
  a hook that invalidates trending cache on scan completion.
- If `ScanHookRegistry` is already wired, just add a trending cache
  invalidation hook. If not, wire it into the scan completion flow.

**Also invalidate `AggregateCache` tags if applicable:**
- `MarketDataService` may cache trending data via `AggregateCache` with
  tags. Invalidate the relevant tag on scan completion.

### Files to modify
- `src/services/scan_hooks.py` (add trending cache invalidation hook)
- `src/api/deps.py` or lifespan (ensure hook is registered at startup)

### Files to reference
- `src/services/trending.py` (invalidate_cache method)
- `src/services/aggregate_cache.py` (tag invalidation)
- `src/services/market_data.py` (MarketDataService)
- `src/collectors/scan.py` (scan completion flow)

## Testing

- Unit test: trending cache is invalidated after scan hook fires
- Unit test: trending data refreshes after cache invalidation
- Unit test: scan hook registry includes trending invalidation
