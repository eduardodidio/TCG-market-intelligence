## User Story

As a developer, I need a service that can match parsed purchase items (from
T01's parser output) to existing `user_collection` entries, so that the
import endpoint can show the user which cards will be updated and with what
confidence level.

## Dev Notes

### Data model (output)

```python
@dataclass
class MatchResult:
    parsed_item: ParsedPurchaseItem    # The original parsed data
    collection_entry_id: int | None    # user_collection.id if matched
    collection_entry_name: str | None  # For display in preview
    collection_set_code: str | None    # For display
    confidence: float                  # 0.0 to 1.0
    match_method: str                  # "exact", "fuzzy_name", "name_only", "none"
    skip_reason: str | None            # Why no match (e.g. "no collection entry")
    already_has_price: bool            # True if entry already has acquisition_price

@dataclass
class MatchReport:
    matched: list[MatchResult]         # confidence > 0
    unmatched: list[MatchResult]       # confidence == 0
    total_parsed: int
    total_matched: int
    total_skipped: int                 # sealed products already filtered by parser
```

### Matching algorithm

The matcher takes a list of `ParsedPurchaseItem` and a user_id, queries the
user's collection, and attempts to match each parsed item.

**Step 1: Load user collection**
```python
# Query all user_collection entries for the user
entries = repo.get_collection(user_id)
# Build lookup indexes for fast matching
```

**Step 2: Build lookup indexes**

Build multiple indexes from the collection entries for cascading match
attempts:

```python
# Index 1: (normalized_name_en, set_code) -> [entry]
# Index 2: (normalized_name_pt, set_code) -> [entry]
# Index 3: (normalized_name_en, collector_number) -> [entry]
# Index 4: (normalized_name_en) -> [entry]  # name-only fallback
# Index 5: (normalized_name_pt) -> [entry]  # name-only fallback
```

**Step 3: Normalize names**

```python
def normalize_name(name: str) -> str:
    """Normalize for accent-insensitive, case-insensitive matching."""
    from unidecode import unidecode
    return unidecode(name).lower().strip()
```

If `unidecode` is not available, fall back to manual accent stripping via
`unicodedata.normalize("NFD", s)` + category filter. Check if unidecode is
already in requirements; if not, use the stdlib fallback (no new deps).

**Step 4: Cascading match for each parsed item**

For each `ParsedPurchaseItem`, try matches in order of confidence:

1. **Exact match (confidence=1.0, method="exact")**:
   `normalized_name_en == entry.name_en` AND `set_code == entry.set_code`
   AND (if collector_number available) `collector_number == entry.collector_number`.

2. **Name + set match (confidence=0.95, method="name_set")**:
   Same as exact but without collector_number check. Try both name_en and
   name_pt from the parsed item against both name_en and name_pt of the
   entry.

3. **Name + collector_number match (confidence=0.85, method="name_cn")**:
   `normalized_name_en` matches AND `collector_number` matches, but
   set_code differs or is missing.

4. **Name-only match (confidence=0.7, method="name_only")**:
   Only name matches (either EN or PT). Multiple collection entries may
   match -- pick the one without an existing `acquisition_price` first,
   then the one with matching quantity, then the first.

5. **No match (confidence=0.0, method="none")**:
   `skip_reason` = "No matching collection entry found".

**Step 5: Quantity handling**

A parsed item with `quantity=4` might map to:
- One collection entry with `quantity=4` (ideal)
- Multiple entries with `quantity=1` each (split)
- One entry with `quantity=1` (partial match)

Strategy: Match to the single entry whose quantity best matches. If the
parsed quantity exceeds any single entry's quantity, still match to the
best candidate and note the mismatch in a warning field. The user can
review in the preview. Do NOT try to split one parsed item across multiple
entries -- keep it simple for V1.

**Step 6: Deduplication**

Multiple parsed items from different orders might match the same collection
entry. The matcher should detect this and keep only the most recent purchase
(latest order_date) or let the user decide in the preview.

### Accent normalization fallback (no unidecode)

```python
import unicodedata

def normalize_name(name: str) -> str:
    """Accent-insensitive, case-insensitive normalization."""
    nfkd = unicodedata.normalize("NFKD", name)
    ascii_text = "".join(c for c in nfkd if not unicodedata.combining(c))
    return ascii_text.lower().strip()
```

This handles Portuguese diacritics (a, e, c cedilla, etc.) without needing
unidecode.

## Edge Cases

- Card name in HTML is PT but collection stores EN name (cross-language match
  via name_pt field)
- Card exists in collection under a different set (e.g. promo vs regular) --
  name-only match with lower confidence
- Same card purchased in multiple orders at different prices -- take the most
  recent or let user choose
- Collection entry already has `acquisition_price` set -- flag as
  `already_has_price=True` so the UI can warn before overwriting
- Parsed card not in collection at all (user sold it, or it's in a different
  user's collection) -- report as unmatched
- Special characters in names: apostrophes (`Sarkhan's Triumph`), commas,
  exclamation marks (`The Eagles Are Coming!`)
- DFC (double-faced cards): parsed name might be front face only while
  collection stores `"Front // Back"` -- normalize by checking if parsed
  name is a prefix of collection name split on ` // `
