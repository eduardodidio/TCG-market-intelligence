# F121-T02: Diagnose and fix Dashboard 500 error on PostgreSQL

**Status:** planned
**Wave:** 0
**Type:** backend

## User Story

As a user, I want the Dashboard page to load correctly when the backend is
connected to Neon PostgreSQL, instead of showing "An internal error occurred".

## Dev Notes

### Problem

The Dashboard shows "An internal error occurred" — a generic 500 from the
global exception handler in `src/api/app.py:530`. The collection page works
fine, so the issue is specific to one of the Dashboard's API calls.

### Dashboard API calls (from `frontend/src/pages/Dashboard.tsx`)

1. `GET /api/v1/market/stats` → `MarketDataService.get_market_summary()` →
   `Repository.get_market_stats()` — the **blocking** call (`stats.error`
   controls the ErrorBanner)
2. `GET /api/v1/collect/health` → `Repository.get_latest_observation_date()`,
   `get_source_card_count()`, `get_stale_cards_count()`,
   `get_recent_errors_count()`
3. `GET /api/v1/collection/summary` → `Repository.get_collection_summary()`,
   `get_collection_total_value()`, `ban_analyzer.get_ban_summary()`

### Investigation results (code review)

Thorough code review confirmed: **all Dashboard repository methods use
SQLAlchemy ORM** — no SQLite-specific raw SQL. The `||` concat and
`ROW_NUMBER() OVER` in catalog.py are standard SQL and PG-compatible.
PRAGMA/VACUUM calls are all guarded by `is_sqlite()`.

**The 500 is NOT a SQL compatibility issue.** Likely causes:

1. **Empty database edge cases** — Neon DB may have no data at all. Check if
   `func.min()` / `func.max()` on empty tables causes serialization issues
   or if Pydantic validation fails on returned types.
2. **Runtime type mismatches** — PG returns proper `date`/`datetime` objects
   vs SQLite returning strings. A `.isoformat()` call on None would crash.
3. **Missing tables** — If `create_all()` fails silently, some tables may
   not exist. Check `collection_errors`, `source_cards` tables.
4. **Connection issues** — Neon pooler might close connections. Check if
   `pool_pre_ping` handles reconnects properly.
5. **`AggregateCache` or service init** — Check if cache initialization or
   the first `get_market_summary()` call has an unhandled exception path.
6. **`ban_analyzer.get_ban_summary()`** — Called inside `collection_summary`
   endpoint, wrapped in try/except but could mask the real error.

### Fix strategy

1. Add structured logging (`structlog`) with try/except around each of the
   3 endpoint handlers to capture the exact traceback.
2. Test locally against the Neon DB: `DATABASE_URL=postgresql://... python -m src.cli.main serve`
3. Fix the root cause (likely a minor type coercion or empty-state issue).
4. If the issue is data-dependent (empty Neon DB), add graceful empty-state
   handling in the affected repository method.
