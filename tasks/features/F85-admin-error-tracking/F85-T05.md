# Task F85-T05 — App Exception Handler + Middleware Integration

**Feature:** F85
**Wave:** 1
**Type:** backend
**Depends on:** F85-T01 (DB model), F85-T02 (error logger service), F85-T03 (JSONL + config)
**Status:** done

## User Story

As an admin, I want all unhandled API exceptions to be automatically
captured with full request context, so that no error goes unnoticed.

## Objective

Wire the `ErrorLogger` into FastAPI's exception handlers and add
request-context capture so every unhandled exception is logged to both
SQLite and JSONL.

## Dev Notes

- Relevant files:
  - `src/api/app.py` — modify `generic_exception_handler`, `lifespan`
  - `src/api/deps.py` — add `get_error_logger` dependency
- Changes to `src/api/app.py`:
  1. In `lifespan`:
     - Create `ErrorLogger` with both sinks (DB + JSONL)
     - Store on `app.state.error_logger`
     - Run retention cleanup on startup (best-effort, wrapped in try/except)
  2. In `generic_exception_handler` (the catch-all for `Exception`):
     - Extract request context: `request.method`, `request.url.path`, `request.query_params`, user_id from `request.state` (if available), `request.state.request_id`
     - Call `app.state.error_logger.capture(exc, request_context=ctx)`
     - Keep existing behavior (return 500 JSON response)
  3. In `http_exception_handler` (StarletteHTTPException):
     - Only capture if status_code >= 500 (server errors)
     - Do NOT capture 4xx (client errors are not application bugs)
  4. In `validation_exception_handler`:
     - Do NOT capture (422s are client input errors)
- Changes to `src/api/deps.py`:
  - `get_error_logger(request: Request) -> ErrorLogger` — returns `request.app.state.error_logger`
  - This lets routers explicitly log errors too (e.g., provider failures caught in try/except)
- The error logger is also useful for non-request contexts (scan workers, CLI).
  For scan/provider errors that are already caught (try/except), add
  `error_logger.capture(exc, extra={"scan_id": ...})` calls in:
  - `src/collectors/scan.py` — the main scan loop's except block
  - `src/collectors/liga_scan.py` — Liga scan error handling
  - Only add the capture call; do not change existing error handling logic
- To get the error_logger in non-request contexts, use a module-level getter:
  - `src/errors/logger.py`: add `_global_logger: ErrorLogger | None = None`
  - `set_global_error_logger(logger)` / `get_global_error_logger() -> ErrorLogger | None`
  - Called in lifespan after creating the logger

## Acceptance criteria

- [ ] Unhandled exceptions in API handlers are captured with full request context
- [ ] Request context includes method, path, query_params, user_id, request_id
- [ ] 500 HTTPExceptions are captured; 4xx are not
- [ ] Validation errors (422) are not captured
- [ ] Error logger is created in lifespan with both DB and JSONL sinks
- [ ] Retention cleanup runs on startup (best-effort)
- [ ] Scan/provider errors are captured via global logger
- [ ] Existing error response behavior unchanged (still returns 500 JSON)

## Test scenarios

- **Happy path:** Endpoint raises ValueError -> error captured with request context
- **HTTP 500:** Endpoint raises HTTPException(500) -> captured
- **HTTP 404:** Endpoint raises HTTPException(404) -> NOT captured
- **Request context:** Verify method, path, request_id in captured error
- **User context:** Authenticated request captures user_id
- **JSONL written:** After exception, JSONL file has one entry
- **Startup cleanup:** Lifespan calls retention cleanup
- **Scan error:** Mock scan failure -> error captured with scan_id in extra
